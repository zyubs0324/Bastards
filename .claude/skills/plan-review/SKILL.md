# Plan Review Skill

Phase/계획 문서를 작성한 직후, `/plan`·`/ecc:plan` 실행 직후, 또는 코드 변경을 커밋하기 전에 호출한다. 각 도메인 전문 에이전트가 `docs/references/` 의 표준 문서를 로딩해 **적대적 리뷰**를 수행하고, 우선순위 보고서 + Verdict 로 집계한다.

## 설계 원칙

- **ECC 범용 에이전트를 재사용**한다 — 좋은 도메인 적합이 있으면 새 전용 에이전트를 만들지 않는다. 대상 스택의 도메인이 ECC 에이전트로 충분히 커버되면 전용 에이전트를 두지 않는다.
- 각 에이전트는 매칭되는 `docs/references/` 참조 문서를 로딩해 리뷰 기준으로 삼는다.
- 리뷰어는 **읽기 전용**(코드 수정 금지). 수정/커밋은 메인 에이전트가 사용자 승인 후 수행한다.
- 코드 모드는 **커밋 전 사용자 승인 게이트**를 강제한다(자동 모드에서도 우회 불가).
- 모든 사용자 대상 출력은 **한국어**.

## Agent Registry (scope tag → 에이전트 → 참조 문서)

모든 리뷰어는 **참조 문서 + 스택 문서**를 함께 읽는다. 코어 문서는 판정 축을 중립어로 서술하고 구체 표기는 스택 문서가 제공하므로, 스택 문서 없이는 무엇을 검사할지 알 수 없다.

| Scope tag | `subagent_type` | 도메인 | 참조 문서 (`docs/references/`) |
|---|---|---|---|
| `arch` | `architect` | SOLID·DRY·KISS·YAGNI, 레이어 경계, 인터페이스 지향 설계 | `software_architecture.md` + 스택 문서 |
| `lang` | **§0-A 가 지정** | 언어·프레임워크 관용성 — 스택 전용 판정 | 활성 스택 문서 §7 (+ §0~§6 대응표) |
| `quality` | `code-reviewer` | 일반 품질, 가독성, 네이밍, 유지보수성, 일관성 | `code_quality.md` + 스택 문서 |
| `security` | `security-reviewer` | 시크릿 하드코딩, 자격증명 저장소, 전송 보안, 입력 검증, 딥링크/외부데이터 | `security_patterns.md` + 스택 문서 |
| `perf` | `performance-optimizer` | UI 스레드 블로킹, 불필요 레이아웃/렌더, 누수, 비동기 패턴 | `performance_patterns.md` + 스택 문서 |
| `test` | `tdd-guide` | 테스트 가능성, 검증 공백, 커버리지 | `testing_patterns.md` + 스택 문서 |
| `comments` | `comment-analyzer` | 주석 부패(rot), 문서-코드 불일치, 중복/군더더기 | `comment_standards.md` + 스택 문서 |

**활성 스택 문서와 `lang` 행의 `subagent_type` 은 `docs/references/project_facts.md` §0-A(활성 스택 표)가 지정한다.** `lang` 에이전트가 `—` 인 버킷은 `lang` scope 만 제외하고 나머지 scope 는 정상 실행한다. **이 스킬 안에 언어 이름이 등장하면 그것이 결함이다**(`README.md` P5).

**기본 scope**(Review Scope 필드가 없을 때): `arch, lang, quality, security, test, perf, comments`

> **7개 전부가 기본이다.** 문서 간 위임(`quality → comments` 주석 판정, `arch·lang → perf` 누수·UI 스레드)의 전이 폐포가 항상 전체이므로, 일부만 켜면 위임한 판정이 **아무도 수행하지 않은 채 사라진다.**

> `--scope` 로 축소하면 **꺼진 scope 때문에 수행되지 않은 판정을 `[HARNESS-DEGRADED]` 로 보고서에 남긴다.** 축소는 사용자 선택이지만 흔적 없이 사라져서는 안 된다.

> 선택된 scope 의 참조 문서나 스택 문서가 없으면 **중단하고 보고**한다 — 패널이 이 문서에 의존한다.

## 모드 / 입력

```
/plan-review [<plan-doc-path>]        # 계획 모드(기본)
/plan-review --code                   # 코드 모드: 미커밋 변경 리뷰 + 승인 후 커밋
/plan-review --scope=arch,lang,perf  # scope 강제(선언/추론 무시)
```

- 인자가 계획 경로이거나 비어 있으면 → **계획 모드**
- `--code` → **코드 모드**
- 모드가 모호하면 한 번 멈추고 묻는다.

## 계획 모드

### Step 1: 계획 문서 찾기

인자가 있으면 그 경로를 사용한다. 없으면 이 프로젝트의 계획 디렉터리에서 가장 최근 파일을 자동 탐지:
```bash
command ls -t .claude/plans/*.md 2>/dev/null | head -1   # `command` — ls 가 eza 등으로 앨리어스된 셸에서 -t 가 조용히 실패하는 것을 방지
```

### Step 2: Review Scope 파싱

계획 문서 헤더의 `**Review Scope**:` 줄에서 쉼표 구분 태그를 읽는다.
```markdown
**Review Scope**: arch, lang, quality, security, perf
```
없으면 기본 scope 7개를 적용한다(Registry 참조).

### Step 3: 에이전트 병렬 실행

`Agent` 도구로 선택된 에이전트를 **한 메시지에서 병렬** 호출한다(`subagent_type` 은 Registry 따름). 각 프롬프트는 자체 완결형이어야 한다(서브에이전트는 이 대화를 못 봄):
1. `docs/references/<참조 문서>` 를 먼저 읽는다 — 이것이 리뷰 표준이다. **출력 형식도 이 문서가 정본이다.**
2. 프로젝트 컨텍스트: `docs/references/project_facts.md` §0 과 **활성 스택 문서**를 읽고 전제로 삼는다 — 계획 헤더의 "변경 파일" 경로를 §0-A 로 배정해 정하고, **프롬프트에 그 경로를 명시한다**(여러 버킷에 걸치면 해당 스택 문서를 모두). 스택 사실은 이 스킬에 중복 기재하지 않는다 — §0 이 정본이다.
3. 리뷰 대상: 계획 문서 전체 + 의존 Phase 의 `## Outcome`(있으면).
4. 적대적 지시: "결함을 적극적으로 찾아라. 우호적 프레이밍 금지. 확신도 80% 미만 발견은 보고하지 마라. 자기 렌즈 밖 결함을 우연히 발견하면 판정하지 말고 `[NOTE-OUT-OF-SCOPE] 위치 — 한 줄 요약` 으로만 남겨라."
5. 실행 제약: 리뷰만, 코드 수정 금지. 200–400 단어(**커버리지 블록 제외**). **모든 발견은 네 정보를 반드시 담는다 — 심각도 · 위치(`파일:라인` 또는 `문서:절`) · 왜 문제인지 · 무엇을 해야 하는지.** 필드명과 배열은 참조 문서 §출력 형식을 그대로 따른다(기본 필드는 `근거/제안` 공통이고, arch 의 `영향:` 처럼 렌즈 고유 필드가 붙는 문서가 있다). 이 항목은 이름을 정하지 않고 **누락을 막을 뿐이다.**
6. **자가진단**(아래 §하네스 무결성)과 **검사 커버리지**(아래 §검사 커버리지)를 함께 보고하라.

#### 하네스 무결성 — 리뷰어 자가진단

설정이 덜 된 상태에서 낸 `PASS` 는 통과가 아니라 검사를 안 한 것이다. 아래를 감지하면 판정보다 먼저 보고한다.

| 단계 | 조건 | 동작 |
|---|---|---|
| **BLOCKED** | 참조 문서·스택 문서를 읽을 수 없음 / 스택 문서 §0 전제 표에 `TODO`·빈칸 | 전체 중단 |
| **DEGRADED** | 코어가 쓰는 논리명의 표기가 스택 문서에 없음 / 위임처 절이 실재하지 않음 / 전제 값이 스택과 모순으로 보임 / 받은 대상이 지정 범위를 벗어남 | 그 항목만 건너뛰고 계속 |

**전제 값이 `—` 로 꺼진 절의 논리명은 DEGRADED 대상이 아니다.** 꺼져서 판정하지 않는 것과 표기가 없어 판정 못 하는 것은 다르다.

> **"이상해 보인다"는 사유가 아니다.** 판정에 필요한 값이 **없거나**, 문서가 가리키는 대상이 **실재하지 않거나**, **받은 입력이 계약 범위를 벗어날 때**만이다. 값이 있는데 낯설면 그대로 판정하고 `DEGRADED` 로 값 검증을 요청하라.

#### 검사 커버리지

참조 문서의 **절별 검사 결과**를 발견과 함께 보고한다. 이것이 없으면 `PASS` 가 "검사했으나 없음"인지 "안 봤음"인지 구분되지 않는다.

**단위는 참조 문서의 판정 절이다.** 판별은 두 조건을 모두 만족하는 절 —

1. **번호가 붙어 있다**(`1.` · `1.1` · `1)` 등)
2. **그 절 본문에 판정 불릿이 있다** — 심각도(CRITICAL/HIGH/MEDIUM/LOW)나 판정(REMOVE/REVISE/KEEP/ADD)을 매기는 불릿

판정 불릿의 대표 표기는 **`- **Flag:**`** 로 통일돼 있다(원칙 병기 시 `- **Flag(SRP):**`). 단 `comment_standards` 는 REMOVE/REVISE 판정을 매기는 불릿이 그 자체로 판정 불릿이므로, 최종 판별은 **낱말이 아니라 역할**이다. `- **Note:**` 는 위임·제외 표시라 판정 불릿이 아니다.

제목에 "Flag"라는 낱말이 있어도 본문에 판정 불릿이 없으면 아니다(`## 1. 검토 기준 (Flag 규칙)` 처럼 하위 절을 묶기만 하는 **컨테이너 헤더**). 프로젝트 관례·출력 형식·심각도 정의·체크리스트·리뷰 시 던질 질문도 아니다.

**마크다운 헤더 레벨로 세지 마라** — 문서마다 `##`·`###` 이 갈린다(`comment_standards` 는 `## 1.`~`## 7.`, `security_patterns` 는 `### 1.`~). 레벨로 세면 비판정 절이 섞여 커버리지 수치가 부풀려지고, 반대로 한 문서에서는 판정 절이 통째로 빠진다.

**판정 불릿 단위로 쪼개지도 마라** — 문서당 30건이 넘어 커버리지가 발견보다 길어진다.

**맨 앞에 판별 결과를 두 목록으로 선언한다.** 어느 번호를 판정 절로 봤고 어느 번호를 왜 뺐는지 밝혀야, 메인이 문서를 읽지 않고도 누락을 잡을 수 있다(Step 4).

**제외 사유는 두 형식만 허용된다** — 판정 절을 제외에 잘못(또는 고의로) 넣는 것을 막는 장치다.
- `§N(컨테이너 — 하위 N.1~N.M)` : 하위 번호가 **판별 목록에 실재**해야 한다. 메인이 집합 연산으로 검증한다.
- `§N(비판정 — "절 제목 그대로")` : 제목을 옮겨 적어야 하므로 문서를 안 보면 쓸 수 없다.

**제외가 없으면 `제외 = {}` 를 명시한다.** 생략은 "제외 없음"이 아니라 **선언 누락**으로 본다.

**전제로 꺼진 판정 절과 대상이 없는 판정 절은 제외가 아니다** — 둘 다 **판별 목록에 넣고** 본문에서 표시한다: 전제 꺼짐은 `—(전제 꺼짐: <전제 이름>)`, 대상 부재는 `✓ + 사유`("함수 선언 없음 — 빌드 메타데이터"처럼 대상에 근거해서). **제외는 문서 구조상 비판정 절(컨테이너·출력 형식·관례·심각도 정의) 전용이다.** 판정 절을 제외로 보내면 "꺼짐/대상 없음/안 봄"이 구분되지 않아 커버리지가 무의미해진다.

**번호 없는 절은 어느 목록에도 선언하지 않는다** — 판별 대상 번호 목록은 번호 붙은 절에서만 나오므로, 번호 없는 비판정 절(예: 번호 없는 `## 출력 형식`)은 누락 검사에 잡히지 않고 제외 선언도 불가능하다(두 제외 형식 모두 `§N` 을 요구한다). 번호가 붙은 비판정 절(예: quality §2·comment §7 출력 형식)만 제외 선언 대상이다.

```
검사 커버리지
  판별  §1.1 §1.2 §1.3 §1.4 §1.5 §1.6 §1.7 §1.8 §1.9 §1.10 §1.11
  제외  §1(컨테이너 — 하위 1.1~1.11) §0(비판정 — "핵심 보정 원칙") §2(비판정 — "출력 형식")

  §1.1 ✓ 신규 함수 최장 32줄        §1.2 ✓ 중첩 3단계
  §1.3 ✓ 중복 블록 없음             §1.4 ⨯
  §1.9 —(전제 꺼짐: 스레딩 모델)
발견 3 · 해당 없음 12 · 전제로 제외 5 · 미검사 1
```

`✓` 검사함 · `—` 전제 게이트로 꺼짐 · `⨯` 미검사

> **발견이 나온 절도 `✓` 로 적고 발견 번호를 병기한다.** `⨯` 는 "위반"이 아니라 **"검사하지 않았다"** 는 뜻뿐이다 — 발견을 `⨯` 로 적으면 미검사 합계가 오염된다.

> **`✓` 중 발견이 없는 절은 "해당 없음 사유"를 덧붙인다.** `✓` 는 자기 신고라, 사유가 없으면 안 보고 찍은 것과 구분되지 않는다. 사유는 **대상에 근거한 짧은 구**로 적는다 — "해당 패턴 없음"(안 봐도 쓸 수 있다)이 아니라 "신규 함수 최장 32줄"(보지 않으면 쓸 수 없다). 완전한 문장은 필요 없다.

> **커버리지 블록은 분량 상한에 포함하지 않는다.** 상한 안에 넣으면 리뷰어가 사유를 뭉뚱그려 D9 가 막으려던 자기 신고 문제가 그대로 돌아온다.

#### 복잡도 기반 배치 분할(토큰 제어)

기준은 **(버킷 × scope) 쌍 수**다. 단일 스택 기본 리뷰는 1 × 7 = 7 로 SMALL 이다.

| Tier | 쌍 수 | 실행 |
|---|---|---|
| **SMALL** | ≤ 7 | 단일 병렬 배치 |
| **MEDIUM** | 8–14 | 2배치 |
| **LARGE** | ≥ 15 | 도메인 그룹별 순차 배치 |

**배치 분할은 토큰 제어 수단이지 조기 종료 수단이 아니다.** CRITICAL 이 나와도 잔여 배치를 실행한다 — 중단하면 나머지 도메인의 커버리지가 사라지고, 그것이 위 §하네스 무결성이 막으려는 "검사 안 한 PASS"다. 부득이 중단했다면 `[HARNESS-DEGRADED]` 로 기록한다.

Scale-up: `security` scope 가 있으면 Tier 와 무관하게 항상 첫 배치에 포함한다.

### Step 4: 결과 집계

**서브에이전트의 출력은 사용자에게 보이지 않는다.** 메인이 중계하지 않으면 사라지고, 재구성하면 `파일:라인`·인용·근거가 빠진다. 그래서 보고서는 3구역으로 고정한다.

```markdown
## Plan Review Report — [대상]
**Agents**: arch, quality, … · **Reviewed**: [날짜]

### 하네스 무결성            ← BLOCKED/DEGRADED 가 있을 때만. 최상단이다
[HARNESS-BLOCKED] <무엇이 없어서 무엇을 판정 못 했는지> · 조치
[HARNESS-DEGRADED] <건너뛴 판정> · 나머지는 정상 수행

### 확정
심각도 순으로. **에이전트 원문 그대로** 옮긴다 — `파일:라인`·인용·참조문서 근거를 생략하지 않는다.
여러 도메인이 같은 위치를 지적하면 묶고 출처를 병기한다.

### 기각
원문 한 줄 + 위치 + **기각 근거**. 건수만 적지 않는다.
다수면 사유별로 묶되 각 건의 위치와 인용 한 줄은 유지한다.

### 판정 변경
원래 값 → 바꾼 값 + 근거. 누구의 판정을 누가 바꿨는지 명시한다.

### 커버리지
**`⨯`(미검사)와 `—`(전제 꺼짐)만 나열하고 나머지는 합계로 줄인다.** 에이전트별 전체 블록을 그대로 옮기면 (버킷 × scope) 수만큼 따라붙어 발견보다 길어지고, D8 이 지키려던 "기각을 명확히 보인다"가 묻힌다. 전체 블록은 사용자가 요청할 때 펼친다.

> **축약하기 전에 사유를 읽는다.** `✓` 의 "해당 없음 사유"는 안 본 절을 가려내는 유일한 수단인데, 그대로 축약하면 그 대조를 아무도 하지 않게 된다. **대상에 근거하지 않은 상투구**("해당 패턴 없음"·"문제 없음")가 있으면 그 절을 `[HARNESS-DEGRADED]` 로 올린다.

> **빠진 절도 대조한다.** 사유 대조는 **적힌 절**만 보고 **빠진 절**은 못 잡는다 — 리뷰어가 9절 중 6절만 세고 전부 `✓` 로 적으면 누락이 드러나지 않는다. **집합이 전부 덮이는지**만 본다.
> ```bash
> grep -oE '^#{2,4} [0-9][0-9.)]*' docs/references/<참조 문서> | grep -oE '[0-9][0-9.)]*' | sort -u
> ```
> 이 번호 목록이 리뷰어의 **판별 ∪ 제외** 와 같아야 한다. **어느 쪽에도 없는 번호가 곧 누락**이다 — 그 절만 되묻거나 `[HARNESS-DEGRADED]` 로 올린다.
>
> 제외 목록도 검증한다 — `컨테이너` 선언은 **하위 번호가 판별 목록에 실재하는지** 집합 연산으로 확인하고, `비판정` 선언은 절 제목이 동반됐는지 본다. 형식을 어긴 제외는 선언 누락과 같이 취급한다.
>
> 개수 비교나 차집합 해석은 쓰지 않는다. 개수는 임계를 정하려면 문서별 참값이 필요하고, 차집합만으로는 잔여가 컨테이너인지 누락인지 메인이 구분할 수 없다 — 그 구분은 본문의 판정 불릿을 봐야 하는데 메인은 참조 문서를 읽지 않는다. **리뷰어가 제외 목록을 명시하면 그 판단이 이미 끝나 있고, 메인은 합집합이 전체를 덮는지만 확인하면 된다.**

```
arch      9절 검사 · 미검사 0
quality  12절 검사 · 미검사 1(§1.7) · 전제 꺼짐 2(§1.9 스레딩 · §1.11 로깅)
```

**Verdict**: BLOCK / PROCEED-WITH-FIXES / PASS
- BLOCK: CRITICAL 1건 이상
- PROCEED-WITH-FIXES: HIGH 있음, CRITICAL 없음 → Known Pitfalls 추가 후 진행
- PASS: CRITICAL·HIGH 없음 → 사용자 승인 후 Phase 진입 가능
```

> 메인 에이전트가 하는 일은 **중복 병합·우선순위 정렬·Verdict 판정**이다. **채택한 것보다 기각한 것을 더 명확히 보인다** — 채택은 결과물에 남지만 기각은 흔적 없이 사라진다.

### Step 5: 후속

- **BLOCK**: 계획 문서의 CRITICAL 수정 후 재리뷰 요청.
- **PROCEED-WITH-FIXES**: HIGH 를 계획 문서의 `## Known Pitfalls` 에 추가 후 보고.
- **PASS**: "리뷰 통과. 사용자 승인 후 Phase 진입 가능." 출력.
- 계획 모드는 코드 작성·커밋을 하지 않는다.

## 코드 모드 (`--code`) — 미커밋 변경 리뷰 + 커밋 전 승인

코드 작성 후, **각 단계 커밋 직전**에 실행. 패널이 **미커밋(작업 트리+스테이지) 변경**(커밋 예정 diff)을 리뷰한다.

### Step 1: 변경 수집

```bash
git status --porcelain && git diff --stat HEAD
```
변경이 없으면 "리뷰할 변경 없음"으로 종료.

### Step 1.5: 버킷 분할 (다중 스택 라우팅)

변경 파일을 `docs/references/project_facts.md` §0-A(활성 스택 표)의 glob 에 **위→아래 first-match** 로 배정한다. **파일이 배정된 버킷만** 리뷰를 만든다 — `(미분류)` 버킷도 파일이 있으면 코어 scope 로 리뷰한다(`lang` 제외).

**에이전트 호출 1건 = (스택 ID, `lang` 에이전트, 참조 문서, 스택 문서 경로, 대상 파일 목록) 5-튜플이다.**
- 리뷰어는 자기 버킷의 **대상 파일 목록 밖을 Read 하지도 판정하지도 않는다.** 목록 밖 파일이 diff 에 보이면 리뷰어가 `DEGRADED` 로 보고한다.
- 리뷰 대상 diff 는 **`git diff HEAD -- <대상 파일 목록>`** 으로 좁힌다 — 전체 diff 를 주면 버킷 분할이 무의미해진다(이것이 교차 스택 배제의 실효 조건).
- 배치 Tier 의 쌍 수는 **파일이 배정된 버킷 수 × scope 수**로 계산한다.

### Step 2: Scope 추론 (2단계)

**1순위**: 활성 계획 문서의 선언된 Review Scope 사용 — 단 **그 계획의 "변경 파일" 경로가 이번 diff 와 겹칠 때만**. 겹치지 않으면 무관한 계획이므로 2순위로 폴백한다(진행 중인 다른 계획이 우연히 최신이라는 이유로 이 변경의 scope 를 지배해서는 안 된다).
```bash
command ls -t .claude/plans/*.md 2>/dev/null | head -1   # `command` — ls 가 eza 등으로 앨리어스된 셸에서 -t 가 조용히 실패하는 것을 방지
```
**2순위(폴백)**: diff **내용**(경로 아님)에서 신호 탐지. **신호 표와 소스 확장자는 각 버킷(Step 1.5)의 활성 스택 문서 §8(scope 추론 신호)을 따른다** — 언어마다 토큰이 완전히 달라지므로 이 스킬에 두지 않는다.

- 신호 없으면 기본 scope 7개(Registry)를 그 버킷에 적용.
- Step 3(계획 모드) 배치 분할 규칙을 추론된 scope 에 적용.

### Step 3: 에이전트 병렬 실행 (diff 대상)

계획 모드 Step 3 와 동일하되 리뷰 대상이 변경분이고 **버킷 단위**(Step 1.5 의 5-튜플)로 호출한다:
1. `docs/references/<참조 문서>` 읽기.
2. 동일 프로젝트 컨텍스트 — 단 스택 문서는 **자기 버킷의 것**(5-튜플의 스택 문서 경로).
3. 리뷰 대상: **`git diff HEAD -- <자기 버킷의 대상 파일 목록>`** + 그 파일 목록. 판단 전 각 대상 파일을 전체로 Read. **목록 밖은 읽지도 판정하지도 않는다.**
4. 동일 적대적 지시 + 80% 확신 임계.
5. `comments` 포함 시 `comment-analyzer` 가 모든 신규/변경 주석을 감사하고, **REMOVE/REVISE** 후보를 `파일:라인` + 위반 규칙과 함께 나열.

### Step 4: 보고 + Verdict

계획 모드 Step 4 와 동일.

### Step 5: 승인 게이트 + 단계별 커밋 (**우회 불가**)

1. 보고서 + Verdict 제시.
2. **주석 정리(심각도 무관)**: `comments` 가 실행됐으면 REMOVE/REVISE 목록 제시. 사용자 승인 시 **메인 에이전트**가 직접 주석을 수정/삭제(서브에이전트는 편집 안 함).
3. CRITICAL/HIGH 가 있으면 수정할지 진행할지 사용자에게 묻는다. 수정 시 영향 scope 만 재리뷰.
4. 사용자의 수동 피드백/조정이 끝날 때까지 대기.
5. **커밋 전 사용자 승인 필수.** 제안 커밋 메시지를 보여주고 명시적 승인("커밋해", "ok" 등)을 받은 후에만 `git commit`. 자동 모드에서도 동일.
6. 승인 후 해당 단계 변경만 스테이지하여 커밋:
   - Conventional Commits, **메시지 한국어**(프로젝트 규칙). 예: `feat: ...`, `fix: ...`, `refactor: ...`
   - `git add <file>` 로 특정 파일만(전체 `git add -A` 지양).
7. 여러 단계가 섞였으면 단계별로 5–6 반복.

## 주의

- 절대 `git push` 하지 않는다. 커밋만.
- 서브에이전트는 리뷰 전용 — 파일 편집 금지.
- 모든 사용자 대상 출력은 한국어.

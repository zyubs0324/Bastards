# 코드 품질 기준 (scope: quality)

> 논리명의 실제 표기는 활성 스택 문서 §2 를 따릅니다. 심각도 정의는 `README.md` 입니다.

## 0. 핵심 보정 원칙

- 판정 기준은 "비개발자 1인이 AI 와 함께 읽고 고칠 수 있는가"다. 영리한 코드보다 읽히는 코드가 이긴다.
- 수치 기준(줄 수·중첩)은 신호일 뿐이다. 넘었어도 읽기 쉬우면 한 단계 낮춰 보고한다.
- 주석의 내용 판정은 comments 문서에 위임한다.

## 1. 판정 기준

### 1.1 함수 길이
- **Flag:** 함수 본문 50줄 초과 → MEDIUM, 100줄 초과 → HIGH.

### 1.2 중첩 깊이
- **Flag:** 조건·반복 중첩 4단계 초과 → MEDIUM. 조기 반환으로 편다.

### 1.3 파일 길이
- **Flag:** 파일 400줄 초과 → MEDIUM, 800줄 초과 → HIGH.

### 1.4 중복
- **Flag:** 같은 로직 블록이 세 곳 이상 반복 → MEDIUM.
- **Flag:** 같은 기획 공식이 두 곳 이상에서 서로 다른 식으로 구현 → HIGH.

### 1.5 수치 하드코딩
- **Flag:** 밸런스 수치(배율·확률·시간·임계치·스탯 기본값)가 코드 리터럴로 들어감 → HIGH. 데이터 파일로 옮긴다.
- **Flag:** 밸런스가 아닌 의미 있는 리터럴(틱 속도, UI 크기 등)이 이름 없이 반복 → LOW. 상수 선언으로 모은다.

### 1.6 네이밍
- **Flag:** `project_facts.md` §0-B 용어집과 다른 도메인 식별자(같은 개념에 새 이름) → MEDIUM.
- **Flag:** 스택 문서 §2 네이밍 규칙 위반, 의미 없는 약어, 불리언에 접두 없음 → LOW.

### 1.7 오류 처리
- **Flag:** 예외를 잡고 아무것도 하지 않거나 로그 없이 넘어감 → HIGH.
- **Flag:** 잘못된 데이터를 기본값으로 대체해 계속 진행(오류 은폐) → HIGH. 로드 시점에 실패시키고 파일명·필드명을 메시지에 담는다.
- **Flag:** 사용자에게 보이는 오류 메시지가 내부 식별자·스택 정보뿐 → LOW.

### 1.8 경계 검증
- **Flag:** 데이터 로더가 범위(음수·0·상한), 필수 필드, 참조 ID 존재 여부를 검증하지 않음 → HIGH.
- **Note:** 신뢰 경계·악의적 입력 관점은 security §3 에 위임한다.

### 1.9 가변성
- **Flag:** 반환한 컬렉션·객체를 호출자가 바꿀 수 있어 원본이 변함 → MEDIUM.
- **Flag:** 규칙 계산 함수가 인자를 변경하거나 숨은 전역 상태를 바꿈 → HIGH. 규칙 계산은 입력→출력 순수 함수로 둔다.
- **Note:** 규칙 모듈 내부에서만 캡슐화된 전투 상태 갱신은 활성 계획 문서의 결정으로 허용된다. 판정 대상이 아니다.

### 1.10 디버그 잔재
- **Flag:** 개발 전용 구역 밖의 로그 호출 → LOW. 반복 경로(틱·프레임)에 있으면 MEDIUM.
- **Flag:** 임시 테스트 값·강제 분기(`if (true)` 류)가 남음 → MEDIUM.

### 1.11 죽은 코드
- **Flag:** 호출되지 않는 멤버·타입, 쓰이지 않는 매개변수 → LOW.

## 2. 출력 형식

```
### [CRITICAL|HIGH|MEDIUM|LOW] 한 줄 제목
- 위치: `파일:라인`
- 근거: 해당 판정 절(§1.x)과 왜 해당하는지
- 제안: 무엇을 해야 하는지
```

발견 뒤에 SKILL.md §검사 커버리지 형식의 블록을 붙인다. 이 문서의 판정 절은 §1.1~§1.11, 비판정 절은 §0·§1(컨테이너)·§2 이다.
